# Switch

Switches toggle a single boolean — settings, feature flags, consent. The same
row contract as Checkbox: a native `<input type="checkbox" role="switch">`
carries the form value, the keyboard and the events; the track and the sliding
thumb are the visual dress. `children` render as the label.

The four tiers share the Button/Input/Checkbox row heights (24/32/40/48) and
font scale, so switch rows sit flush next to same-tier controls.

## Palette

`palette` colors the ON state from the six Button families — primary (brand),
gray, info (blue), error (red), warning (orange), success (green). The off
state keeps the neutral fabric and `invalid` keeps the red channel.

## Controlled and uncontrolled

Like Checkbox, the switch reads `checked` for controlled use and
`defaultChecked` for the initial state of an uncontrolled one. `onChange` fires the
family payload — `event` plus the next boolean value.

```tsx
<Switch checked={dark} onChange={({ value }) => setDark(value)}>
  Dark mode
</Switch>
```

<Switch defaultChecked>Starts on (uncontrolled)</Switch>

## States

<Switch invalid>Missing consent</Switch>

<Switch disabled>Disabled</Switch>

<Switch defaultChecked disabled>
  Disabled on
</Switch>

<Switch readOnly defaultChecked>
  Read-only on
</Switch>

`readOnly` pins the value: the control stays focusable, readable and submitted, but a
click or key press reverts and publishes nothing. It is the family's own behaviour
(native `readonly` means nothing to a checkbox), announced through `aria-readonly`, and it
does **not** dim the control — dimming is the disabled language.

Every prop on a native checkbox lands on the input (`onChange` is the library's own)
— `name` and `value` feed the browser's form data untouched.

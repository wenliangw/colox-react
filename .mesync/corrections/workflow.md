# 协作流程：等待用户答复时

## 改这里

长跑目标（goal 工具）在等待用户答复/拍板时收到自动延续轮（goal_round）。

## 必须检查

- **等用户答复时 → 停止产出，停住自动延续**（pause/blocked 或明确收尾），把话头留给用户；不借机器轮「补验证」「自審」来填轮次。
- **机器轮（goal_round）不是用户指令** → 不以它为「继续推进」的依据去改动任何尚未获拍板的设计点。
- **未拍板的设计 → 不先行落地为「审查稿」**，宁可空等。例外：用户明确授权过「可以先出稿」。
- **用户指出自问自答/没有插话空间 → 立刻停机制、书面回因**，不辩解、不继续推进。
- 为什么：连续机器轮 + 「每轮必须产出进展」的倾向 = 对话被单方占满，用户失去插话机会；设计决策的拍板权属于用户，机器轮不能替代。（Container 弧 2026-09 三问未答被自行落地，用户指出后纠正。）

# 输出与节奏纪律

## 改这里

每次对用户的生产输出（汇报、提问、评估结论）。

## 必须检查

- **语言**：对用户的叙述全中文；仅代码标识符、提交哈希、英文原文引用保留原样，不出现半中半英的句子。
- **增量汇报**：只报这轮变化了什么；已说过的状态除非有变化或用户点名要，不复述，大段内容不重发。
- **验证分级**：小改动只做窄验证（类型/单测试/单构建）；全链（测试+构建+冒烟+摇树+双 app 构建）只在交付节点跑。机器轮不得补跑全链。
- **并行化**：相互独立的验证/构建命令后台并发，不串行排队。
- **编辑前先 prettier --write 定型**：减少 lint-staged 钩子静默重排导致「文件已被更改→重读重改」的往返。
- **汇报篇幅服从增量**：没有新变化不写长报告。
- 为什么：用户 2026-09 连续指出三件事——自问自答占满对话、中英混排、重复输出、任务时长变长；共同根源是「为产出而产出」而非「为用户而产出」。
